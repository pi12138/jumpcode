# v0.2.1 release notes

[Project home](../../README.en.md) · [Usage](../usage.en.md) · [Development](../development.en.md) · [简体中文](v0.2.1.md)

A stable patch release that fixes the standard-stream handle lifetime after Windows scheduled servers detach from the console, and explicitly requests a new window for remote projects. Commands and configuration remain compatible with v0.2.0; existing pairings and certificates continue working.

## Changes since v0.2.0

- Retain the original standard-stream objects before detaching a Windows scheduled server from its console. This prevents GC finalizers from closing handles that Windows has already released and reused. Closing a reused handle can affect logs, sockets, or the Go runtime IOCP and cause exits such as `runtime: netpoll failed`. This fix addresses that handle lifetime defect.
- `jc client .` (`jc c .`) and direct `jc host:folder` commands on Windows explicitly request a new VS Code window for remote projects, avoiding replacement of a different project in the current window. VS Code activates an existing window if the same folder on the same SSH host is already open; Jumpcode does not track windows.
- Add bilingual guides for separate LAN development hosts, SSH reverse forwarding from cloud servers, Tailscale, multiple pairings, and recovery after network changes.

## Installation and upgrades

Artifacts include a Windows amd64 ZIP, Linux amd64 tar.gz, `release.json`, and `SHA256SUMS`. Archives contain the executable, bilingual guides, and these release notes. See the [project home](../../README.en.md#installation) for installation and checksum verification.

Upgrading from v0.2.0 does not require pairing again or reinstalling the task. Stop a scheduled server, replace `jc.exe` at the **installation path referenced by the task**, then start it and check the version and status:

```powershell
jc task stop
# Replace jc.exe at its original installation path
jc --version
jc task start
jc task status
```

Tasks store the absolute executable path. Replacing another copy on your terminal's `PATH` does not update the task. The server startup log should show `v0.2.1`.

For manual background mode, run `jc server stop`, replace the executable, and restart with the original listen configuration. Stop foreground servers with `Ctrl+C` first. On Linux, replace `jc`. Preserve credentials, certificates, and logs in the user configuration folder. Upgrades from v0.1.1 or earlier still require [legacy task cleanup](../usage.en.md#legacy-task-cleanup).

## Validation and known limitations

- Local checks passed: the complete Linux test suite with race detection, Linux/Windows `go vet`, both platform builds, and Windows test cross-compilation. The release workflow runs native Windows/Linux CI on the tagged source before building and verifying the archives.
- A new Windows regression test uses an isolated child process to simulate release and reuse of old standard-stream handles, forces GC, and checks that reused handles and server responses remain valid. URI tests verify the new-window parameter and ensure special characters in folder paths cannot change it.
- Automated checks do not cover full Windows desktop interaction, actual VS Code window behavior, or long-running stability. Check VS Code for the final SSH connection result. A window may still flash briefly when a scheduled server starts.
- Network, credential, and configuration limitations from v0.2.0 remain: the server supports Windows only, the client Linux only, and jc listen/server addresses require explicit IPv4 addresses. Automatic listeners do not push new addresses to clients or update the paired Linux SSH destination. See the [usage guide](../usage.en.md) for more limitations.
