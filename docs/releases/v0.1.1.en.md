# v0.1.1 release notes

[Project home](../../README.en.md) · [Usage](../usage.en.md) · [Development](../development.en.md) · [简体中文](v0.1.1.md)

A stable maintenance release fixing Windows sign-in task installation and garbled errors, with a new command to run an installed task immediately.

## Changes since v0.1.0

- Fix `jc s startup install` failing with malformed task XML or an encoding-switch error. Task files now use UTF-16LE with a BOM and a matching declaration, including support for Chinese and other Unicode paths.
- Decode Task Scheduler error output using the Windows code page, preserving the underlying failure and avoiding garbled Chinese messages.
- Add `jc server start` (`jc s start`) to run the current user's installed sign-in task immediately, using the executable path, language, and listen settings saved during installation.
- Wait up to 10 seconds for the server control endpoint to become ready. Missing tasks, rejected requests, and readiness timeouts return clear errors. Starting an already running task reports its status; a standalone background server prompts the user to run `jc s stop` first.
- Record manual start requests, readiness, and startup failures in the existing `server.log` without recording pairing tokens.
- Add tests for command arguments, readiness, startup timeouts, repeated starts, and background-mode conflicts, and update the bilingual management guide.

## Installation and upgrade

Artifacts include a Windows amd64 ZIP, Linux amd64 tar.gz, `release.json`, and `SHA256SUMS`. Archives include the executable, bilingual guides, and these notes. See the [project home](../../README.en.md#installation) for installation and checksum verification.

Existing pairing settings and installed sign-in tasks from v0.1.0 remain valid. Pairing again is not required. If the server is running, run `jc s stop`, then replace `jc.exe` at its original path. With a task already installed, run:

```powershell
jc s start
jc s status
```

If installation previously failed because of the encoding issue, first run `jc s startup install --listen auto`, then run the commands above. Explicit listen addresses can also be saved during installation. `jc s start` accepts neither `--listen` nor `-d`. To change task settings, uninstall the task and reinstall it with the desired options.

`jc s stop` stops the current server gracefully while keeping automatic startup at the next sign-in. `jc s startup uninstall` removes the task and stops its server.

## Validation and known limitations

- The release workflow runs formatting checks, `go vet`, tests, and builds on Windows and Linux, with race detection on Linux. It also verifies release checksums and the Linux CLI.
- Windows tests validate generated XML through the actual Task Scheduler without creating or running a task. Startup-flow tests use a scheduler substitute and a local control endpoint. Automated verification does not cover the complete task start/stop lifecycle, user sign-in, or actual VS Code desktop interaction.
- A startup timeout does not cancel the scheduler request. The task may still start or retry later; check `jc s status`, `jc s startup status`, and the log.
- The server supports Windows and the client supports Linux. No public relay or IPv6 support is provided.
- Pairing configuration has no process lock; run credential creation and revocation sequentially. Direct Windows opens of `host:~/folder` still query the SSH home directory without an application timeout.
- Automatic listen addresses are discovered at startup. Restart after interface changes and pair again if the client's saved server address changes.
- `pair list/status` only reads local records. Logs do not rotate automatically. Check the VS Code window for the final connection result.
