# v0.2.0 release notes

[Project home](../../README.en.md) · [Usage](../usage.en.md) · [Development](../development.en.md) · [简体中文](v0.2.0.md)

A stable feature release with unified Windows sign-in task management through `jc task` and automatic listener updates after network changes. This version replaces the v0.1.1 task commands. Remove old tasks before upgrading.

## Changes since v0.1.1

- Add `jc task install/uninstall/start/stop/status`, with aliases `jc t` and `jc t st`. Remove `jc s startup` and `jc s start`.
- Manage the current user's sign-in task through native Windows Task Scheduler COM calls. The task directly runs the same `jc.exe server`, which detaches from its console in the same process. There is no additional resident launcher. Standard output, standard error, and panic traces go to `server.log`; a brief startup flash remains possible.
- `install` only registers the task; `start` waits up to 10 seconds for readiness. `stop` requests graceful shutdown through an authenticated local control endpoint. `uninstall` stops the server before deleting the task while retaining credentials, certificates, and logs. Task and manual background modes use separate runtime state files.
- `auto` subscribes to Windows IPv4 address and interface change notifications. Events are combined over about 500 milliseconds before adding or removing listeners. Unchanged listeners and existing connections remain available, and the PID and certificate fingerprint stay the same. Foreground, manual background, and task modes all support this behavior.
- Keep the process and local control endpoint running when no addresses are available, then resume listening after recovery. Enumeration or bind failures trigger retries every three seconds. Identical errors are logged once; healthy operation does not poll interfaces.
- Preserve the original `auto` configuration when starting a manual background server. Status commands show actual listeners and distinguish a running process from a ready service when no listeners exist. Stopping remains available while offline.
- Update bilingual installation, mode switching, upgrades, logging, architecture, and development guides.

## Installation and upgrade

Artifacts include a Windows amd64 ZIP, Linux amd64 tar.gz, `release.json`, and `SHA256SUMS`. Archives include the executable, bilingual guides, and these notes. See the [project home](../../README.en.md#installation) for installation and checksum verification.

To migrate a sign-in task from v0.1.1 or earlier, run this command with **the old jc executable before replacing it**:

```powershell
jc s startup uninstall
```

This stops the old task's server and removes the task while retaining pairing settings. Put the new `jc.exe` in a permanent installation folder, then run:

```powershell
jc task install --listen auto
jc task start
jc task status
```

If you already replaced the executable, follow [Legacy task cleanup](../usage.en.md#legacy-task-cleanup) to end and delete the old task before installing the new one. For a test build already using the current `jc task` mechanism, keep the same path and listeners, run `jc task stop`, replace the executable, and run `jc task start`. Reinstallation is unnecessary.

For manual background mode, run `jc s stop`, replace the executable, then run `jc s --listen auto -d`. Stop a foreground server with `Ctrl+C` first. Keep the user config folder to retain pairings and certificates. On Linux, replace the `jc` executable.

## Validation and known limitations

- Local checks passed: the complete Linux test suite with race detection, Linux and Windows `go vet`, both platform builds, Windows test cross-compilation, and documentation links. The release workflow additionally runs native Windows/Linux CI and verifies archive checksums and the Linux CLI.
- Dynamic listener tests use controlled events, address snapshots, and real loopback HTTPS. They cover listener changes, connection preservation, recovery after losing all addresses, bind retries, state updates, and stopping without changing machine adapters. Actual Windows notification delivery during Wi-Fi/VPN switching has not been verified on a local desktop.
- Automated checks do not cover user sign-in triggering, complete task management, or VS Code desktop interaction. Console tests run in isolated child processes. A console executable detaches after startup, so a brief window flash cannot be ruled out.
- The server supports Windows and the client supports Linux. No public relay or IPv6 support is provided. Each client stores one server address and must pair again if it changes; automatic listening does not discover or push a new address to clients.
- A `jc task start` timeout does not cancel the scheduler request. The process may still be waiting for the network or retrying. Inspect status and logs. `stop` retains sign-in startup; `uninstall` removes the task.
- All explicitly configured listen addresses must bind at startup. Failed automatic candidates are retried while other listeners remain available. Logs are appended without automatic rotation.
- Pairing settings have no process lock; run credential creation and revocation sequentially. Direct Windows opens of `host:~/folder` still query the SSH home directory without an application timeout. `pair list/status` only reads local records. Check the VS Code window for the final connection result.
